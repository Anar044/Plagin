# Smart Horeca — тестирование QR → касса на отдельном стенде

Версия: 2026-10-29. Этот документ относится **только к тестовому стенду** и черновым PR:
- Smart Horeca / backend / Pages: https://github.com/Anar044/anarsystem/pull/214
- C# плагин: https://github.com/Anar044/Plagin/pull/4

**Статус**: код прошёл компиляцию и статические проверки, но ещё не проверен с установленным iikoFront, кухонным и фискальным принтерами. Никакой автоматической установки нет.

## A. Контроль совместимости и сохранение предыдущей версии

1. В тестовом iikoFront откройте **О программе** и зафиксируйте точную версию. Для ранее указанного iikoFront 8.4.7010.0 выбран API **V8Preview5**, официально совместимый с линейкой 8.4. Источник: https://iiko.github.io/front.api.doc/versioning.html
2. На тестовой кассе найдите исходный каталог плагина внутри `...\Front.Net\Plugins\<папка вашего плагина>`. **Не создавайте копию старого и нового плагина одновременно в Plugins:** это может запустить два экземпляра плагина и дублировать события.
3. Закройте iikoFront штатно, скопируйте каталог плагина (с `Manifest.xml`, DLL, зависимостями и файлами) в папку резервной копии **вне** Plugins. Сохраните конфигурацию `smarthoreca.json` и связанные локальные файлы; не удаляйте `%AppData%\iiko\CashServer`.
4. Если ZIP получен из GitHub или браузера Windows, **сначала** проверьте источник и снимите отметку блокировки: правый клик по ZIP → «Свойства» → «Разблокировать» (если есть) → «Применить». **Только затем** распакуйте и копируйте файлы. Если распаковали до снятия блокировки, на тестовом ПК можно проверить свойство файла `Zone.Identifier` и снять его **только с проверенных файлов тестовой папки** PowerShell-командой (от имени администратора):

```powershell
$folder = 'C:\Program Files\iiko\iikoRMS\Front.Net\Plugins\KassaSH'
Get-ChildItem -LiteralPath $folder -Recurse -File | Unblock-File
```

Эта команда не меняет глобальную политику безопасности .NET и не касается других папок. Не используйте `loadFromRemoteSources`, массовое отключение SmartScreen или исключения антивируса для решения `FileLoadException 0x80131515`. Снимать блокировку допустимо только с **достоверно полученной** тестовой сборки.

5. Используйте только GitHub Actions **артефакт из тестовой ветки PR №4**. Не скачивайте DLL из иных веток и не копируйте контракт `Resto.Front.Api.V8Preview5.dll` в плагин — его предоставляет iikoFront. Установочный пакет должен содержать `Manifest.xml`, иначе установка не считается законченной. По документации iikoFront плагины устанавливаются отдельными подпапками `Plugins`: https://iiko.github.io/front.api.doc/directories.html
5. **Первые испытания без кухонной печати**: пока ещё не проверены и POS Bridge backend, и локальные права, оставьте `Enabled=false`, `AllowOrderCreation=false`, `AllowKitchenPrint=false`. Новая DLL должна вести себя как старая. Если не загрузилась — немедленно откатите каталог из резервной копии и снимите журнал загрузки плагина.

**Проверка версии перед включением:** в присланном логе до установки работала версия `1.4.4.17500-prod`, а наша тестовая сборка идентифицируется как `1.3.41.14636` по собственному GitVersion. Это не доказательство совместимости или равенства набора функций. Перед использованием QR сравните набор возможностей предыдущей версии с исходниками данной ветки и проверьте все старые события на тестовом стенде. Не ставьте тестовую сборку в рабочий ресторан.

## B. Тестовый сервер и база данных

1. Разверните именно ветку **`feature/qr-order-internal-core-20261029`** из PR №214 в отдельном Cloudflare Pages тестовом окружении, привязанном к **тестовой D1**, не к рабочей. Не используйте боевое меню и реальный ресторан для тестового оформления.
2. Убедитесь, что тестовый сервер Smart Horeca использует тестовый RMS и зарегистрированный `pluginId`/точный `departmentId` этой тестовой кассы. Не разрешайте плагину работать с чужими ресторанами/организациями.
3. Настройте в серверных секретах Cloudflare для тестового окружения `QR_ORDER_RATE_SECRET`, `QR_POS_BRIDGE_TOKEN`, `PLUGIN_INGEST_TOKEN`. Никаких секретов в браузере, GitHub Actions, скриншотах и чатах. Сверьте с безопасным локальным файлом `smarthoreca.json`.
4. Привяжите опубликованное тестовое QR-меню к **одному** выбранному тестовому ресторану. Возьмите простой товар без модификаторов, с точным GUID из POS и ценой AZN, совпадающей в D1 и на кассе. Для режима TABLE настройте **реальный GUID стола в POS**.

## C. Включение только тестового POS

После успешной проверки загрузки старого функционала:
1. Отдельно настройте кассового оператора с минимальными правами на создание заказа и его **PIN только в защищённом конфигурационном файле**.
2. В `smarthoreca.json` добавьте узел `QrPosBridge` из документа `docs/QR_POS_BRIDGE_V1.md`, укажите **URL тестового Cloudflare Pages** с путём `/api/qr-menu/pos-bridge`, идентификатор плагина и секреты.
3. **Только на тестовой кассе**, после резервной копии, поставьте `Enabled=true`, `AllowOrderCreation=true`, `AllowKitchenPrint=true`. Пока подтверждение кухонного принтера не проверено, проводите первый QR-заказ на столе с тестовой кухней/принтером, не на рабочем оборудовании.
4. При запуске плагин должен отправлять `hello` не реже раза в минуту. В `/qr-order-admin.html` должен появиться статус «Касса подтвердила поддержку QR-заказов». Если его нет, **не пытайтесь включить приём QR**: проверьте соответствие URL, `pluginId`, `departmentId`, токенов и статус backend.
5. Только после статуса «POS-мост готов» включите «Разрешить гостям оформлять QR-заказы» и создайте стол.

## D. Первый тест заказа

1. Откройте QR стола из `/qr-order-admin.html`. Выберите 1–2 простых блюда, добавьте комментарий и отправьте.
2. В Smart Horeca: `AWAITING_POS → LEASED → POS_OPEN`. Заказ должен получить **настоящий** `posOrderId` и номер POS. На кассе должен быть **ровно один** заказ с правильным столом, товарами, количеством, ценами, комментарием.
3. После `ackCreated` плагин посылает `PrintOrderItems`. На тестовом принтере должен появиться **ровно один** корректный кухонный билет. В Smart Horeca `kitchen_status=PRINTED`; при неясном результате — `CHECK_REQUIRED`, **без автоматической повторной печати**.
4. После реальной тестовой оплаты на кассе: номер и подпись **фискального** документа должны поступить из кассового устройства. Только тогда Smart Horeca может показать `CLOSED` и `PAID_AT_POS`.
5. Перезагрузите браузер — прежний чек не должен превращаться в повторный заказ. Новый заказ разрешён только после явного действия «Начать новый заказ».
6. Проверьте отключение интернета/кухонного принтера между подтверждением и печатью: ни второй POS-заказ, ни второй кухонный билет не должны создаваться автоматически. Неизвестный результат требует ручной сверки.
7. Проверьте ошибочную цену и отсутствующий POS товар. Безопасный повтор из кабинета должен разрешаться только для `POS_VALIDATION_FAILED`. При `POS_RESULT_UNKNOWN` повтор без ручной сверки **запрещён**.

## E. Что передать после первой попытки

Нужны **только безопасные технические факты**: точная версия iikoFront; версия плагина/API, которую он загрузил; этап проверки, на котором произошло отклонение; текст ошибки без токенов и PIN; снимок статуса тестового QR заказа; подтвердился ли кухонный билет и фискальный чек.

Не присылайте `smarthoreca.json` целиком, токены, PIN, данные банковских карт или реальные фискальные данные гостей. Если отправляете лог, уберите секреты, локальные данные работников и клиентов.

## F. Как откатить

1. Выключите в тестовом Cloudflare QR-заказы в настройках ресторана.
2. Верните в локальной конфигурации `Enabled=false`, `AllowOrderCreation=false`, `AllowKitchenPrint=false`.
3. Завершите iikoFront, удалите **только** новую тестовую версию каталога плагина и восстановите его резервную копию **в исходный каталог**. Оставьте системные каталоги CashServer и базу данных нетронутыми.
4. Перезапустите тестовый iikoFront и убедитесь в доступности обычного POS/событий.
5. Проводите дальнейшие изменения только в тестовом окружении, пока не проверены все сценарии.
